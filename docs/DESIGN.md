# 设计论证（DESIGN）

## 为什么是一个工具，而不是一堆脚本

脚本能被 agent 调用，但**"记得调用"本身不可靠**。把它注册成工具后，
模型看到的是一条带 description 的能力，而不是藏在某个目录里的文件；
工作区约定（AGENTS.md「发布前侵权审核（必做）」）再把"发布前必须调用"钉死。
两件事合起来才构成"每次发布都会审"。

## 为什么技能载荷与插件载荷是同一份（`skill/`）

一开始技能与插件是两份目录，规则在两边各有一份副本。这必然漂移：
改了 Python 扫描器却忘了同步技能副本，用户走哪条路径就得到哪套结论。

现在 `skill/` 是单一真源：

- 插件运行器直接执行 `skill/scripts/release_audit.py`
- `scripts/install-skill.sh` 把同一个目录复制进 `$DSH_HOME/skills/`
- 校验方式是把两边 `diff -r` 逐字节比对（已在交付时执行）

## 为什么退出码 1/2 是"结果"而不是"失败"

扫描器用退出码表达结论：`0` 干净、`1` 仅警告、`2` 存在阻断项。
运行器如果把非零退出当成子进程失败，那么**每一次发现阻断项的审核都会变成工具崩溃**——
模型拿到的是一个裸错误，而不是"哪里有问题、怎么改"。所以运行器只把
"进程起不来 / 被信号杀掉 / stdout 不是 JSON" 当失败。

## 为什么只注册一个工具

`findings[]` 已含类别、级别、证据、依据、处置，`report` 是可直接展示的 Markdown。
再拆成"查许可证""查密钥"多个工具，只会让模型多花轮次拼装同一份报告，
并给"只调其中一个就当审过了"留下空子。

## 为什么判定必须锚定外部标准

许可证兼容性、商标、著作权都有法定或权威文本。若判定来自模型直觉，
同一份代码在不同会话可能得到不同结论，而这种工具的错误代价是**用户据此发布侵权内容**。
所有规则因此指向 [skill/references/verdict-basis.md](../skill/references/verdict-basis.md)
列出的出处（SPDX license list、FSF GPL FAQ、CC 官方、choosealicense、商标法/著作权法条文），
并且在报告里逐条带 `basis` 字段。

## 为什么只读

审核工具写文件没有任何必要，而写入会带来两个后果：
被审项目被污染、并发调用互相干扰。当前实现只读、无锁、`isConcurrencySafe: true`。
